- snapshot schedule: não configurado;
- branch default: `main`.

Tamanhos aproximados observados:

| Tabela | Tamanho |
| --- | ---: |
| `transactions` | 232 kB |
| `accounts` | 64 kB |
| `categories` | 48 kB |
| `users` | 48 kB |

`transactions` aparecia com aproximadamente **742 rows** nas estatísticas disponíveis.

Sinais:

- locks ativos: **0** na coleta;
- waste estimado de bloat: 8 kB em `transactions` e 16 kB em `accounts`;
- vários índices possuem poucos/zero scans, mas têm apenas ~8–16 kB e o banco é pequeno;
- contadores de sequential scan são altos em termos cumulativos, porém sobre tabelas muito pequenas;
- `pg_stat_statements` não está instalado, então slow-query ranking detalhado não estava disponível.

### Decisão

Não instalar `pg_stat_statements`, remover índice ou adicionar índice somente para preencher o item 36.

O item 35 passou a registrar `durationMs` + cardinalidades seguras em export, Dashboard, Forecast e import. Esses sinais devem indicar quando a próxima análise SQL é necessária.

Gatilhos para ação:

- operação cara com regressão reproduzível;
- crescimento material de rows/tamanho;
- lock/timeout observado;
- query plan concreto apontando scan/índice;
- limites serverless sendo atingidos.

Referências:
